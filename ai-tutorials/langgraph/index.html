Graph and workflow

LangGraph

LangGraph builds agents as graphs. Small Python functions share one state dictionary, and edges decide which function runs next. Loops, memory, and a pause for a human are normal, not special cases.

IntermediateLangGraph 1.x · Python 3.10+

Nodes, edges, state

AnalogyA graph is a board game. Nodes are squares. State is the token you move. Edges are the arrows. Because an arrow can point backward, a square can be repeated until the job is done.
Data flow
State dict→Node function→Partial update→Edge→Next node

LangChain gives you models and tools. LangGraph decides the order and keeps state. One model call with no branch does not need a graph. Reach for one when the path depends on a decision, a retry, or a person. Returning a partial dict merges. Replacing the whole message list by accident wipes history.

Starter

state = {"url": "https://example.com", "title": ""}

def write_title(state):
    return {"title": "Notes"}  # merge this key; do not rebuild the whole dict

print({**state, **write_title(state)})

Example

Fetch transcript, then title, then post is a graph even though nobody chooses the next step. The names make retries obvious.

A node is a function. State is one dictionary (or a typed dict) those functions read and update. An edge says which node runs after which. Because an edge can point backward, a step can repeat until the job is done.

LangChain gives you models, messages, and tools. LangGraph decides the order and keeps the state. For one model call with no branch, a plain function is simpler. Reach for a graph when the path depends on a decision, a retry, or a person.

Example: YouTube video to a blog post

AnalogyA fixed workflow is a recipe card. The graph does not make it smarter. It makes each step a named station you can retry without rerunning the whole recipe.
Data flow
START→Fetch→Title→Post→END

The same stations show up in real jobs: invoice PDF to fields to a ledger row, a pull request to tests to a comment, classify then retrieve then draft. Put each station in its own function so a failure names the station.

Starter

from typing import TypedDict

class BlogState(TypedDict):
    url: str
    title: str

def fetch(state: BlogState) -> dict:
    return {"title": "How agents keep state"}

print(fetch({"url": "https://youtu.be/demo", "title": ""}))

Example

A video-to-blog pipeline that fails on the transcript should not call the writing model. The edge into “title” never runs.

Three fixed steps: pull a transcript, write a title from it, write the post from both. Nothing here needs a model to choose the next node. The graph still helps because each step has a name, a state field, and a place to retry.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class BlogState(TypedDict):
    url: str
    transcript: str
    title: str
    post: str

def fetch_transcript(state: BlogState) -> dict:
    # Real code calls a transcript API. This stand-in keeps the shape obvious.
    return {"transcript": f"Transcript of {state['url']}: agents, tools, and state."}

def write_title(state: BlogState) -> dict:
    return {"title": "How agents keep state"}

def write_post(state: BlogState) -> dict:
    return {"post": f"# {state['title']}\n\n{state['transcript']}"}

graph = StateGraph(BlogState)
graph.add_node("fetch", fetch_transcript)
graph.add_node("title", write_title)
graph.add_node("post", write_post)
graph.add_edge(START, "fetch")
graph.add_edge("fetch", "title")
graph.add_edge("title", "post")
graph.add_edge("post", END)
app = graph.compile()
print(app.invoke({"url": "https://youtu.be/demo", "transcript": "", "title": "", "post": ""}))

Same shape, other jobs

  • Invoice PDF → fields → ledger row → email to finance.
  • Pull request → tests → summary comment. The test node can loop back once if the command fails.
  • Support macro: classify → retrieve policy → draft → send.

A conditional edge

AnalogyA conditional edge is a fork in the road. The sign is a function that reads state and returns the name of the next square. Cap the loop or the fork points at itself forever.
Data flow
Fetch result→route()→title or fetch again→stop after N tries

Store `attempts` in state. Graphs make the loop visible. They do not make it safe. Map every return value of `route` to a real node, including the failure node.

Starter

def route(transcript: str, attempts: int) -> str:
    if attempts >= 2:
        return "give_up"
    if len(transcript) < 20:
        return "fetch"
    return "title"

print(route("", 1))

Example

A short transcript retries once. A second failure should land on an error node a human can see, not a third silent fetch.

def route(state: BlogState) -> str:
    if len(state["transcript"]) < 20:
        return "fetch"   # try again, or swap in a clearer error node
    return "title"

graph.add_conditional_edges("fetch", route, {"fetch": "fetch", "title": "title"})

Cap the retries in state (attempts: int) or this edge will loop forever. Graphs make the loop visible. They do not make it safe by themselves.

A support agent that chooses tools

AnalogyA tool loop is a conversation between a model and a toolbox. The model asks. The tool node answers. The edge back to the model is the loop. Text with no tool call is the exit.
Data flow
User→Model→Tool call?→Tool node→Model→Final text

`create_react_agent` is a prebuilt graph: model node, tool node, loop. When refunds must not take the same path as status checks, write the nodes yourself. Streaming shows each node as it finishes, which is how you see “it refunded before it looked up the order.”

Starter

ORDERS = {"A17": "shipped on 3 March"}

def lookup_order(order_id: str) -> str:
    return ORDERS.get(order_id, "unknown")

print(lookup_order("A17"))

Example

“Where is A17?” may call lookup and answer. “Refund A17” should take a different edge that stops for a person.

The user asks “where is order A17?”. One node calls the model. If the model requested a tool, a second node runs it and loops back. If the model answered in text, the graph ends.

from langgraph.prebuilt import create_react_agent
from langchain.tools import tool

ORDERS = {"A17": "shipped on 3 March", "C40": "waiting for stock"}

@tool
def lookup_order(order_id: str) -> str:
    """Look up shipping status by order id, such as A17."""
    status = ORDERS.get(order_id)
    return f"{order_id} {status}." if status else f"{order_id} is unknown."

# agent = create_react_agent(model, tools=[lookup_order])
# agent.invoke({"messages": [("user", "Where is order A17?")]})
print(lookup_order.invoke({"order_id": "A17"}))

create_react_agent is a prebuilt graph: model node, tool node, loop. When you outgrow it, write the nodes yourself so the branch is explicit — refunds go to a different node than status checks.

Use case: refund vs status

“Where is A17?” may call lookup_order and answer. “Refund A17” should not take the same edge. Route on the intent to a node that stops and asks a person. Money and deletions are the usual places teams add that pause.

Pause, then resume

AnalogyAn interrupt is a pause button on one square. The board saves itself. A person presses resume later, possibly on another machine, and the token is still on that square.
Data flow
Run until refund node→Checkpoint→Human approves→Resume→Refund node runs

Compile with a checkpointer and interrupt before the dangerous node. `MemorySaver` dies with the process, which is fine for a tutorial and wrong in production. Use Postgres or Redis when more than one server handles traffic. Resume with the same thread id.

Starter

thread = {"id": "customer-asha", "status": "waiting"}
approved = True
thread["status"] = "resume" if approved else "waiting"
print(thread)

Example

The UI shows the order id and the amount, then an Approve button. The graph does not spend money while it is waiting.

Compile the graph with a checkpointer and interrupt before the dangerous node. The process can exit. Later you resume with the same thread id and the human’s decision in state.

Use a real checkpointer (Postgres, Redis) when more than one server handles traffic. MemorySaver dies with the process, which is fine for a tutorial and wrong for production.

Streaming (app.stream) lets a UI show each node as it finishes. That is how you debug “it refunded before it looked up the order”: you see the node order, not a single final string.

Advantages and limits

AnalogyUse a graph when you need to point at a step and say “it failed here.” If you cannot name the steps, you do not have a graph yet. You have a prompt.
Data flow
Named steps?→Yes→StateGraph→No→One function

Branches, retries, and parallel steps are reviewable because they are drawn. Any chat model you can call can sit in a node. A single completion should stay a function. Prefer the message reducers in the docs when you add chat history, so you append messages instead of replacing them.

Starter

def needs_graph(steps: int, has_branch: bool) -> bool:
    return steps > 1 or has_branch

print(needs_graph(1, False))

Example

A straight invoice email is a function. A support flow that loops on missing order ids is a graph.

  • Branches, retries, and parallel steps are drawn, so they are reviewable.
  • State, checkpoints, and human approval are built in.
  • Any chat model LangChain can call can sit in a node.
  • A single completion does not need a graph. Extra nodes hide simple bugs.
  • You have to think in state updates. Returning a partial dict merges; replacing a whole messages list by accident wipes history. Prefer the message reducers in the docs when you add chat history.

Practice

  • Add an attempts field and stop after 2 failed fetches.
  • Split “refund” and “status” into two nodes with a conditional edge.
  • Interrupt before refund and print the state you would show an agent in a UI.
  • Name one workflow at your job that is a straight line, and one that must loop.
